# Одит: Алгоритъм "none" и Timing Attack

## Дата
Май 2025

## Обхват
Проверка на два конкретни класически проблема в JWT имплементации:
1. Отхвърляне на токени с `"alg": "none"`
2. Constant-time сравнение на подписи (защита срещу timing attack)

---

## 1. Алгоритъм `none` — ЗАЩИТЕН

Отхвърлянето става на **три независими слоя**:

| Слой | Файл | Механизъм |
|------|------|-----------|
| Парсване | `jwt/private/jose.nim:24-31` | `strToSignatureAlgorithm` → `SecurityError` при `NONE` |
| Конструкция на хедър | `jwt/private/jose.nim:48-63` | `isSecureAlgorithm` допълнително филтрира |
| Верификация | `jwt.nim:119-144` | `verify()` изисква **изрично подаден** алгоритъм от потребителя — не го чете от токена. Проверява `token.header.alg != alg` и `alg == NONE → false` |

### Защо е важно

Атаката с `"alg": "none"` е класическа уязвимост в JWT библиотеки. Ако един токен може да бъде приет с алгоритъм "none", подписът не се проверява и всеки може да фалшифицира токен.

### Допълнителна защита: Algorithm Pinning

`verify()` **не чете** алгоритъма от токена — той се подава изрично от потребителя:

```nim
proc verify*(token: JWT, secret: string, alg: SignatureAlgorithm): bool =
  if token.header.alg != alg:
    return false
```

Това предотвратява и **algorithm confusion атаки** (напр. превключване от RS256 към HS256).

## 2. Constant-time Comparison — ЗАЩИТЕН

| Алгоритъм | Файл | Подход |
|-----------|------|--------|
| HMAC (HS256/384/512) | `jwt/private/utils.nim:48-57` | `secureCompare` — XOR-OR акумулатор |
| RSA (RS256/384/512) | `jwt/private/crypto.nim:99-115` | BearSSL PKCS#1 verify + `secureCompare` върху дайджестите |
| ECDSA (ES256/384/512) | `jwt/private/crypto.nim:146-168` | BearSSL native verify, дайджестът се нулира след употреба |

### Имплементация на `secureCompare`

```nim
proc secureCompare*(a, b: openarray[byte]): bool =
  ## Constant-time comparison to prevent timing attacks
  if a.len != b.len:
    return false
  var diff = 0
  for i in 0..<a.len:
    diff = diff or (int(a[i]) xor int(b[i]))
  diff == 0
```

**Никъде в кода не се използва `==` за сравняване на подписи.**

### Защо е важно

При обикновено `==` сравнение, операцията спира на пъввото различно байтче. Хакер може да измери времето за отговор на сървъра и байт по байт да открие правилния подпис (timing attack). XOR-OR акумулаторът винаги обхожда всички байтове независимо от съдържанието.

---

## 3. Допълнителни мерки за сигурност

- **HMAC ключ ≥ 32 байта** — `bearHMAC` в `crypto.nim` отхвърля по-къси ключове
- **Нулиране на буфери** — дайджестите се нулират с `zeroMem` след употреба
- **PS256/384/512** — дефинирани в enum-а но връщат `false` (не са имплементирани — по-добре отколкото неправилна имплементация)

---

## Заключение

Имплементацията е **сигурна** по отношение на двата проверени проблема:
- ✅ Алгоритъм `none` се отхвърля на три независими слоя
- ✅ Сравнението на подписи е constant-time навсякъде
- ✅ Algorithm pinning предотвратява confusion атаки
